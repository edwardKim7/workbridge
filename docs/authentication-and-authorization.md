# 인증과 권한

## 채널별 인증 방식

WorkBridge는 웹과 모바일의 사용 방식이 달라 인증 수단을 분리합니다.

| 채널 | 인증 | 상태 저장 |
|---|---|---|
| JSP 웹 | Spring Security 세션, CSRF | 서버 HttpSession |
| Flutter | Bearer Access Token, Refresh Token | 앱 Secure Storage + 서버 Refresh Token 해시 |

직원, 역할, 활성 상태와 업무 권한은 두 채널이 같은 DB 모델을 사용합니다.

## 웹 로그인

로그인 성공 시 세션 ID를 변경해 세션 고정 공격을 막습니다. 상태 변경 요청은 CSRF 토큰을 확인합니다. JavaScript 요청은 JSP가 전달한 CSRF 헤더 이름과 값을 사용합니다.

비밀번호는 BCrypt로 비교합니다. BCrypt 입력 한계를 고려해 신규 비밀번호는 UTF-8 기준 72바이트 이하로 제한합니다.

존재하지 않는 로그인 ID도 더미 해시 비교를 수행하며, 화면에는 사용자 존재 여부를 구분하지 않는 공통 오류 메시지를 표시합니다.

## 로그인 실패 잠금

기본 정책은 연속 5회 실패 시 15분 잠금입니다. 횟수와 시간은 환경변수로 변경할 수 있습니다.

```text
ACTIVE
  └─ 로그인 실패 누적
       └─ 한도 도달 → LOCKED
                       ├─ 잠금 시간 만료 → 다음 로그인에서 초기화
                       └─ ADMIN 해제 → 즉시 초기화
```

로그인 성공 시 실패 횟수와 잠금 시각을 초기화합니다. 실패 로그에는 입력 비밀번호를 저장하지 않습니다.

## 모바일 토큰

Access Token은 짧은 수명의 JWT입니다. Refresh Token은 난수 문자열이며 DB에는 SHA-256 해시만 저장합니다.

갱신 순서는 다음과 같습니다.

1. Refresh Token 해시로 DB 행 조회 및 잠금
2. 폐기, 만료, 사용자 상태 확인
3. 기존 Token 폐기
4. 새 Access Token과 Refresh Token 발급
5. 새 Refresh Token 해시 저장

동일 Refresh Token을 다시 사용하면 갱신을 거부합니다. 로그아웃과 계정 비활성화 시 관련 Refresh Token을 폐기합니다.

Access Token 요청에서도 현재 직원 상태를 다시 조회하므로 사용자가 비활성화되면 남은 만료시간과 관계없이 보호 API 접근을 차단합니다.

## 역할과 메뉴 권한

기본 역할은 `ADMIN`, `SALES`, `APPROVER`, `VIEWER`입니다. `role_menu`는 메뉴별 읽기, 쓰기 권한을 저장합니다.

- 쓰기 권한은 읽기 권한 없이 부여할 수 없습니다.
- 하위 메뉴 읽기를 허용하면 상위 탐색 메뉴도 읽을 수 있어야 합니다.
- 모든 역할은 기본 이동 경로인 대시보드 읽기 권한을 유지합니다.
- ADMIN은 직원, 역할 관리 접근 권한을 유지합니다.

JSP 사이드 메뉴는 읽기 권한을 기준으로 구성하지만, URL 직접 호출은 서버 권한 검사에서 다시 차단합니다.

## 업무 소유권

역할 권한을 통과해도 Service에서 업무 대상에 대한 소유권을 확인합니다.

- `SALES`: 자신이 담당한 고객, 영업기회, 활동만 변경
- `APPROVER`: 자신에게 지정된 `REQUESTED` 결재만 처리
- 결재 요청자: 자신의 `DRAFT`만 수정, 요청, 취소
- `ADMIN`: 관리 범위의 전체 데이터에 접근하되 감사 로그 기록
- `VIEWER`: 부여된 조회 기능만 사용

## 관리자 보호 규칙

다음 변경은 시스템 관리 경로를 잃지 않도록 차단합니다.

- 현재 로그인한 사용자의 자기 비활성화
- 마지막 활성 ADMIN 비활성화
- 마지막 활성 ADMIN의 ADMIN 역할 제거
- ADMIN 역할의 필수 관리 메뉴 권한 제거

마지막 관리자 여부를 확인할 때 관련 역할 행을 잠가 동시에 두 관리자가 서로의 권한을 제거하는 상황을 막습니다.

## 동시 수정

직원, 부서, 권한, 고객, 영업기회, 활동, 결재에는 버전 값을 사용합니다. 수정 SQL은 ID와 현재 버전을 함께 조건으로 사용하고, 영향 행이 0이면 `409 OPTIMISTIC_LOCK_CONFLICT`를 반환합니다.

결재 승인, 반려는 버전뿐 아니라 현재 상태도 조건으로 확인합니다. 앱의 버튼 비활성화는 사용자 경험을 위한 보조 수단이며 최종 중복 차단은 DB UPDATE 결과로 판단합니다.

## 감사 로그

다음 이벤트를 감사 대상으로 기록합니다.

- 로그인 성공, 실패, 잠금, 잠금 해제
- 직원 상태와 역할 변경
- 역할, 메뉴 권한 변경
- 고객, 영업기회, 활동 변경
- 결재 요청, 승인, 반려, 취소
- 외부 인터페이스 전송, 재처리
- 데이터 이관 실행

비밀번호, Access Token, Refresh Token, 세션 ID는 기록하지 않습니다. 연락처, 이메일, 사업자번호와 외부 전문은 저장 전 마스킹합니다.

## 외부 배포 시 추가할 항목

현재 구현에는 IP, 사용자별 요청 제한, MFA, 비밀번호 변경 주기, 분산 세션 저장소가 포함되지 않습니다. 인터넷 환경에서는 HTTPS, Secure Cookie, Reverse Proxy, Secret Manager, 관리자 접근 제한과 함께 추가해야 합니다.
